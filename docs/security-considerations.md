# LibreChat & Code Interpreter Sandbox (RCE) セキュリティ考察・リスク評価レポート

本ドキュメントは、閉域網環境における **LibreChat** および **Code Interpreter (RCE) サンドボックス** のセキュリティアーキテクチャ、脅威モデル、多層防御の有効性、および今後の運用に向けたセキュリティ推奨事項を体系的に考察・まとめたものです。

---

## 1. 脅威モデルと想定される攻撃シナリオ

Code Interpreter（コード実行環境）を持つシステムでは、通常の Web アプリケーションへの攻撃に加え、**「正当な機能として任意のプログラムコードが実行される」** という固有のリスクが存在します。

```
[ 想定される攻撃ベクトル ]
  ├─ ① データ窃取・C2通信 (Egress Exfiltration / Command & Control)
  ├─ ② ラテラルムーブメント (横方向への侵入拡大: MongoDB, Nginx, 社内LAN)
  ├─ ③ リソース枯渇・DoS攻撃 (CPU/メモリ枯渇, Fork Bomb, ディスク枯渇)
  ├─ ④ 他ユーザーのセッション・機密データへの不正アクセス (マルチテナント侵害)
  ├─ ⑤ コンテナエスケープ & ホストOS乗っ取り (特権昇格, カーネル脆弱性の悪用)
  └─ ⑥ プロンプトインジェクションによる意図しない不正コードの自動実行
```

---

## 2. 実装された多層防御（Defense in Depth）のセキュリティ評価

本システムでは、単一の防御機構に依存せず、**5層のセキュリティ境界（Security Boundaries）** を設けています。

| 防御層 | 適用技術 | 防御する脅威 | 有効性・評価 |
|:---|:---|:---|:---|
| **Layer 1: 境界防御 (Nginx/TLS)** | TLS 1.2/1.3, HSTS, Rate Limiting | 盗聴、改ざん、ブルートフォース攻撃 | ✅ 社内クライアントとの通信暗号化とDoS緩和 |
| **Layer 2: ネットワーク隔離** | Docker `internal: true`, Bridge 分離 | ① C2通信/外部情報流出, ② ラテラルムーブメント | ✅ デフォルトルート不在により外部パケット即時破棄 |
| **Layer 3: OS・プロセス分離** | NsJail, Linux Namespaces (PID/NET/MNT) | ④ マルチテナント侵害, ⑤ ホストOS探索 | ✅ 独立一時ディレクトリ `/tmp/{uuid}` & Loopback限定 |
| **Layer 4: リソース制御** | cgroups v2 (CPU: 2core, Mem: 2GB, PIDs: 50) | ③ リソース枯渇・DoS (Fork Bomb 等) | ✅ 30秒タイムアウトで強制SIGKILL |
| **Layer 5: ストレージ・データ保護** | MinIO S3 プレフィックス分離, 24h TTL | ④ 他セッションのファイル盗取・残存リスク | ✅ 物理的・論理的スコープ制限と自動消滅 |

## 3. 各脅威に対する詳細セキュリティ考察

### 3.1 外部情報流出（C2通信・データ窃取）への耐性
- **現状**: `rce-isolated` ネットワークが `internal: true` で構成されており、コンテナ内に外部ゲートウェイが存在しません。
- **考察**: 仮に攻撃者が Python コード内で `socket`, `requests`, `urllib` を使って機密データを外部サーバーに送信しようとしても、カーネルレベルで `Network is unreachable` となり即時失敗します。DNS トンネリング等も外部 DNS へのルートがないため成立しません。

### 3.2 フロントエンド層・社内LANへのラテラルムーブメント耐性
- **現状**: `public-frontend`（Nginx, MongoDB）と `rce-isolated`（Worker, Redis, MinIO）が完全に分離されたブリッジネットワークに収容されています。
- **考察**: Worker サンドボックスから MongoDB（ユーザー情報・過去ログ）や Nginx、またはホストが所属する社内ネットワークへの直接通信はルーティングが存在しないため不可能です。

### 3.3 マルチテナント（セッション間）データ分離の安全性
- **現状**: 
  1. コード実行ごとにランダムな UUID ディレクトリ（`/tmp/{session_uuid}`）が作成される。
  2. NsJail により、当該ディレクトリ以外は Read-Only または非マウント。
  3. MinIO 上でも `/{session_id}/` 単位でオブジェクトが隔離される。
- **考察**: 実機テスト（`Session A` で作成したファイルを `Session B` から探索・読み取り試行）において、100% の分離（`FileNotFoundError`）が実証されており、セッション間のファイル混在や覗き見リスクは極めて低く抑えられています。

### 3.4 認証とシークレット管理
- **現状**: 
  - 実運用シークレット（`JWT_SECRET`, `CREDS_KEY`, APIキー等）は `.env`（`.gitignore` 済み）で管理。
  - 公開リポジトリ用テンプレート（`.env.example`）にはダミー値および汎用ドメイン（`librechat.example.com`）を使用。
- **考察**: GitHub 等への誤プッシュによるクレデンシャル漏洩リスクは適切に低減されています。

## 4. 今後の運用に向けたセキュリティ推奨事項（Hardening Recommendations）

本システムを長期運用・本番運用するにあたり、以下の追加対策を推奨します：

### ① 社内 PKI による正式 SSL/TLS 証明書の適用
- 現在は自己署名証明書（開発用）を使用しているため、ブラウザで警告が表示されます。
- **推奨**: 社内の認証局（Enterprise PKI / Active Directory CS等）から自社ドメイン（例: `librechat.internal.domain` や `your-domain.local`）に対する正規の証明書を発行し、`nginx/certs/server.crt` に配置することで、中間者攻撃（MITM）の検知とユーザーの利便性を両立します。

### ② ユーザー登録制限の運用切り替え（運用開始後）
- 初期構築完了後、不要なアカウント作成を防ぐため、`.env` の設定を切り替えることを推奨します：
  ```env
  ALLOW_REGISTRATION=false  # 一般ユーザーの新規登録を無効化（管理者が招待/手動作成）
  ```

### ③ MinIO バケットの自動クリーンアップ（Lifecycle Rule）
- 現在は `SESSION_TTL_HOURS=24` が設定されていますが、MinIO のバケットライフサイクルポリシー（Lifecycle Rules）を併用し、24時間を経過した一時ファイルが物理ストレージ上からも確実に完全消去されるよう定期監視・パージを設定することを推奨します。

### ④ コンテナおよび Python ライブラリの定期脆弱性スキャン
- `rce_requirements.txt` に含まれるパッケージ群（`scikit-learn`, `pandas`, `litellm` 等）について、定期的に `pip-audit` や Trivy を用いた CVE 脆弱性検査を実施することを推奨します。

## 5. 総合結論

本システムの設計・実装は、**「コード実行という高リスクな機能を、多層防御によって局所化・無力化する」** というセキュリティ原則（Least Privilege, Defense in Depth, Complete Mediation）に忠実に準拠しています。

外部ネットワークの完全遮断、独立サンドボックス実行、セッション別ストレージ分離が実機検証を通じて確認されており、**エンタープライズ閉域網における極めて安全な LLM & Code Interpreter 運用基盤**が確立されています。
